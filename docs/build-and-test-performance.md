# Build & Test Performance — root causes, rules, measurements

*Developer-facing. Stable. Introduced 2026-09 (v0.19.x).* Companion to
[AGENTS.md §1 "Target Directory & Cache Management"](../AGENTS.md#target-directory--cache-management)
and [§2 "Test Binary Layout"](../AGENTS.md#test-binary-layout--one-binary-per-harness-class),
which carry the binding rules. This page carries the *why* and the numbers, so the rules can be
re-derived when the workspace changes.

## Why

`target/` on a developer machine grew to 17–18 GB within a day and had to be `cargo clean`ed
repeatedly; local and CI cycles were slow. The audit below found that almost none of that was
"stale" data — it was **parallel copies of the same crates**, produced by three multipliers that
the workspace layout and its own documented workflow were actively encouraging. Each multiplier
has a mechanical fix, and each fix is now enforced (by config, by `cargo hakari verify`, or by
`scripts/check-guardrails.sh`).

## The mechanism (what cargo actually does)

Cargo names every artifact `<crate>-<hash>` where the hash covers the **feature set, every
profile setting, the compile mode (check / build / test / doc), the target kind (lib / bin / each
test file) and the rustc version** (`compute_metadata()` in cargo's `compilation_files.rs`).
Anything that changes one of those produces a *new* file next to the old one; `target/` is never
garbage-collected (cargo's automatic cache cleaning, stable since 1.88, only touches `~/.cargo`;
target-dir GC is open as rust-lang/cargo#13136).

`RUSTFLAGS` / `--cfg` are deliberately *excluded* from that hash so that toggling them rebuilds
**in place** — a time cost, not a disk cost. That is why `--cfg reqwest_unstable` lives in
`.cargo/config.toml` and must be carried by every invocation, and why `cargo llvm-cov`
(`-C instrument-coverage`) keeps its own `target/llvm-cov-target/`.

## The three multipliers, measured on this workspace (2026-09-02, M-series Mac, 10 cores)

Baseline before any change, from a clean tree:

| Step | Wall time | `target/` | Notes |
|---|---:|---:|---|
| `cargo build` (dev, default members) | 76 s | 2.7 GB | with the repo's `jobs = 4`; 67 s at `jobs = 10` — the build is critical-path-bound on `ahma_mcp` (33 s lib + 18 s test harness) |
| `cargo test --no-run` | +79 s | 9.4 GB | **143 executables = 3.18 GB** (median 20 MB; `ahma_mcp` tests ~62 MB each); `incremental/` 3.0 GB, one session per test crate |
| `cargo test --no-run --no-default-features` | +64 s | 15.5 GB | recompiled only **16** workspace units, yet added **5.9 GB** and doubled the executables to 275: every flavour re-links every test binary |
| then `build -p ahma_core`, `build -p ahma_common`, `check -p ahma_http_bridge`, `build --bin ahma`, `build -p ahma_mcp --features simplify`, `test --no-run -p ahma_mcp`, `build -p xtask`, `clippy --all-targets`, `test --no-run` | — | **18 GB** | zero source changes. `-p ahma_core` alone recompiled ~70 third-party crates (tokio, rmcp, both reqwests, axum, the sigstore tree) into new file names because a single package unifies features differently from the workspace |

### 1. Feature flavours of the workspace crates

`ahma_mcp` had a **no-op default feature `android = []`** used only as a CI test selector
(`--features android`); `ahma_bin` defaults to `simplify`; `ahma_tui` to `tui`. CI's Linux leg
built three flavours in one job (`--no-default-features`, then `-p ahma_tui -p ahma_bin`
with defaults, then `-p ahma_mcp --features simplify`), the macOS "android" leg a fourth, and
AGENTS.md told developers to test quarantined features "directly with `-p`". Each flavour is a
second `ahma_mcp` (the critical-path crate) and a second link of all its test binaries, and
none of those objects can be shared through sccache.

**Fix:** the `android` feature is deleted (tests are selected by name); every CI job and every
documented local command uses **default features, whole workspace**; the lean
`--no-default-features` build is proven by the clippy step in check mode (no codegen, no
links). Windows was already compiling `simplify` for `-p ahma_bin`, so the canonical flavour
adds no work anywhere — it only removes flavours. CI also sets `CARGO_PROFILE_DEV_DEBUG` equal
to `CARGO_PROFILE_TEST_DEBUG`; with only the test profile overridden, the `cargo build -p
ahma_bin` pre-step and the nextest run compiled every workspace crate twice.

### 2. Third-party feature unification differs between `-p X` and the workspace

Cargo unifies a dependency's features across *the packages selected on the command line*.
`cargo build -p ahma_core` sees fewer dev-dependencies than `cargo build`, resolves `tokio`,
`serde_json`, `reqwest`, … with fewer features, and gets different hashes for ~70 crates.

**Fix:** `workspace-hack/` generated by [cargo-hakari](https://docs.rs/cargo-hakari) — a crate
that depends on the *union* of every member's third-party features, which every member depends
on, so every invocation resolves to the same set. `xtask` is excluded from unification so its
`ureq` stack does not leak into the product build. Regenerate after any dependency edit
(`cargo hakari generate && cargo hakari manage-deps`); `cargo hakari verify` runs in the
guardrail script. Reported by Oxide on omicron: 1.7× cumulative command time, 78 → 55 GB.

### 3. One executable per `tests/*.rs` file

Every top-level `tests/*.rs` is its own crate and its own statically-linked executable that
carries the full dependency closure (`ahma_mcp`'s rlib alone is 118 MB) plus its own
`incremental/` session. `ahma_mcp` had 93 such files, `ahma_http_bridge` 25 (19 of which each
recompiled the 2,138-line `tests/common/` from source). ~35 of the files were under 190 lines.
cargo-nextest runs each test in its own process regardless of binary layout, so merging files
loses no isolation and no parallelism (matklad, *Delete Cargo Integration Tests*: 3× faster
suite compile, 5× smaller artifacts on cargo's own suite).

**Fix:** one root file per harness class per crate (`unit`, `e2e`, `stress`, …; see the AGENTS.md
table), former files as `mod`s. This also let `.config/nextest.toml` throttle and grant CI
retries **only** to the binaries that actually spawn subprocesses — previously
`binary_id(~ahma_mcp::)` throttled ~66 deterministic in-process binaries and gave them retries
its own policy says they must not have. A guardrail rejects new top-level `tests/*.rs` files.

## Other findings and what was done with them

| Finding | Action |
|---|---|
| Repo `.cargo/config.toml` set `[build] jobs = 4` for a Raspberry Pi 5; capped every developer machine | Removed; machine limits go in `~/.cargo/config.toml` (documented in that file) |
| `ring` and `directories` were direct deps with zero uses | Removed. `ring` then still arrived transitively as a **second** rustls crypto provider next to the mandatory `aws-lc-rs` — through `rcgen`'s and `quinn`'s default features and an explicit `rustls::crypto::ring` in the bridge's QUIC config. All three now select `aws-lc-rs`; `scripts/check-dependency-graph.sh` (pre-push and Fast Tier) fails if any dependency's defaults bring `ring` back into the product graph on any CI platform |
| `ahma_core` used `tokio = "full"`, `ahma_mcp` bare `tokio = "1.53.1"` | Both on the workspace-curated feature list |
| macOS Spotlight (`mds_stores`, `mdworker`) consumed 3–4 cores indexing rebuilt objects | Documented: add `target/` to Spotlight's Search Privacy list |
| `scripts/stress-test.sh` used `-p ahma-http-bridge` (hyphenated, never valid) and `-p ahma_mcp --bin ahma` (bin lives in `ahma_bin`) | Fixed with the new binary names |
| `check-guardrails.sh` ran a `cargo test … --test tool_tests <path>` filter | Replaced by a real smoke test plus `cargo hakari verify` and the layout check |

## Findings that need a product/design decision (not done here)

Ranked by expected payoff; each is a real change in what ships or how a feature is wired, so it
is recorded rather than applied unilaterally.

1. ~~**`sigstore-verification` is 451 of the 682 crates in `Cargo.lock` (66 %)** for one call
   site (`ahma_update/src/verify.rs`, `ahma verify` / `ahma update`).~~ **done: option (c).**
   `sigstore-verification` is gone; `ahma verify` / `ahma update` verify GitHub Build
   Provenance on `sigstore` 0.14 directly (`default-features = false`, features `verify` +
   `sigstore-trust-root` + `rustls-tls`). Measured on the same tree, deduped compile graph
   (`cargo tree --workspace -e normal --prefix none | sed 's/ (\*)$//' | sort -u | wc -l`):

   | Metric | Before | After |
   |---|---:|---:|
   | Workspace compile graph | 533 | **490** |
   | `ahma_update` subtree | 399 | **357** |
   | `cargo tree --workspace -e normal --prefix none \| sort -u \| wc -l` | 724 | **670** |
   | `grep -c '^name = ' Cargo.lock` | 689 | **677** |
   | `cargo tree --workspace --duplicates \| grep -cE '^[a-z]'` | 84 | **81** |
   | `syn` majors | 3 (1.0, 2.0, 3.0) | **2** |
   | `hashbrown` versions | 5 | **4** |
   | `deny.toml` advisory ignores | 3 | **1** |

   Gone from the graph: `oci-client` (and its `oci-spec`/`jwt` subtree), `json-syntax` +
   `locspan` + the seven `lexical-*` crates, `proc-macro-error`, `smallstr`, `snap`'s old
   caller, `ed25519-dalek`, `p384`, `x509-parser`, `ahash`, `syn 1.0`, and the duplicate
   `darling`, `indexmap`, `strum` and `base64 0.13`. The two advisory ignores those crates
   forced (RUSTSEC-2024-0370, RUSTSEC-2026-0215) were deleted, not re-justified.

   **What stays, and why**: `sigstore`'s own `verify` feature enables `fulcio` → `oauth` →
   `openidconnect`, an upstream feature chain ahma cannot cut, so `openidconnect` (and with
   it `rsa`, hence the one remaining `deny.toml` ignore, RUSTSEC-2023-0071) is still in the
   graph. `tough` also stays: it is what `sigstore-trust-root` uses to fetch the public-good
   TUF trust root, and replacing it would mean pinning trust material in the binary — exactly
   the key-rotation problem this trust model exists to avoid.
2. ~~**`oauth2 5.0` in `ahma_http_mcp_client` pins its own `reqwest 0.12` + `rustls-tls`.**~~
   **done.** `oauth2` is now `default-features = false` and token requests go through
   `oauth_http::OAuthHttpClient`, an `oauth2::AsyncHttpClient` over the workspace's `reqwest
   0.13`. Because `openidconnect` reaches `oauth2` the same way, this is also what makes
   `cargo tree -i reqwest@0.12` **empty**: the second `reqwest` major and the `ring`
   provider its `rustls-tls` feature enabled are gone from the graph. Together with the
   single-provider change (table above), every TLS-using crate
   in the product now shares one `reqwest`, one `rustls`, one `rustls-webpki` and one crypto
   provider.
3. ~~**`opentelemetry` / `-otlp` / `_sdk` is a 206-crate subtree compiled unconditionally.**~~
   **done.** Gated behind `ahma_common`'s `otel` cargo feature (off by default), forwarded
   through `ahma_mcp/otel` and `ahma_http_bridge/otel` — unlike `simplify` (finding 4), the
   code that calls `ahma_common::observability` lives inside those two crates themselves
   (`ahma_mcp/src/utils/logging.rs`, `ahma_http_bridge/src/main.rs` and `src/peer.rs`), not in
   an optional sibling crate, so the feature could not be pushed out to `ahma_bin` alone and
   both crates do pay a second flavour — but only when asked for it. Every function in
   `observability.rs` keeps the same public signature regardless of the feature (a
   `Box<dyn Layer>` return type, not the concrete `OpenTelemetryLayer`), so no call site needs
   its own `#[cfg]`; without the feature, `create_otel_layer` is a hard no-op even when
   `--opentelemetry <url>`/`OTEL_EXPORTER_OTLP_ENDPOINT` is set. Deliberately **not** the same
   trade as the rest of this document: `otel` is a second CI-tested flavour — `job-cargo-nextest`
   in `build.yml` (gates every merge queue run and push to main) builds, clippies and nextests
   it on its Linux leg — and release binaries ship it (`job-release-binaries`), but it costs
   nothing on the canonical dev/test/clippy cycle every other finding here protects.
4. **`ahma_mcp` is the long pole** (33 s lib + 18 s test harness on the critical path; 118 MB
   rlib; ~180 source files). Splitting leaf modules into their own crates widens the graph so
   more of it compiles in parallel and shrinks the crate that every edit–test cycle recompiles.
   **Partly done (2026-09-03):** every module that imported nothing — or only `ahma_common` —
   from the rest of the engine is now its own crate, re-exported from `ahma_mcp` under its old
   path so no caller changed: `ahma_simplify` (also the end of what was ahma_mcp's only cargo
   feature — see finding 3 for the `otel` exception; the analyzer is an optional dependency of
   `ahma_bin`), `ahma_update` (takes the whole
   sigstore/zip/tar/flate2 tree off ahma_mcp's direct dependency edge), `ahma_vault`,
   `ahma_log_monitor`, `ahma_output_optimizer`, `ahma_harness_guard`, `ahma_bundle`. That is
   ~14 k of ~100 k source lines and 41 of 183 files. What is left is not leaf-shaped:
   `livelog/` needs `operation_monitor`, `shell_pool`, `config` and `sandbox`; `egress/` needs
   `sandbox::profiles`; `tool_availability/` needs `sandbox` and `config`; `hooks/`, `setup.rs`
   and `uninstall.rs` need the adapter and service. The next cut, if wanted, is
   `operation_monitor` + `shell_pool` (they depend only on `utils`), which would unblock
   `livelog`.
5. **`ahma_http_bridge` ↔ `ahma_mcp` dev-dependency cycle.** Legal, but it means the bridge's
   test helpers can never move into `src/` and the bridge lib is compiled in two contexts.
   A dedicated `ahma_e2e` test crate that depends on both would remove the cycle.
6. `pub mod test_utils` in `ahma_mcp` is compiled into every release binary (3,196 lines).
   `#[cfg(any(test, feature = "test-utils"))]` with the feature enabled from dev-dependents
   keeps the "compile once, reuse from every test binary" property and trims the shipped
   artifact.

## How to measure again

```bash
cargo clean
cargo build --timings            # target/cargo-timings/*.html: per-unit durations, critical path
cargo test --no-run
du -sh target target/debug/deps target/debug/incremental
find target/debug/deps -maxdepth 1 -type f -perm -u+x ! -name '*.dylib' ! -name '*.rlib' ! -name '*.d' | wc -l
# The flavour test: after a full build, any of these must recompile (almost) nothing.
cargo build -p ahma_core 2>&1 | grep -c Compiling
cargo test --no-run -p ahma_mcp 2>&1 | grep -c Compiling
cargo tree --workspace --duplicates          # duplicate crate versions
cargo tree --workspace -e normal --prefix none | sed 's/ (\*)$//' | sort -u | wc -l  # deduped compile graph
cargo tree -p ahma_update -e normal --prefix none | sed 's/ (\*)$//' | sort -u | wc -l  # the sigstore subtree
```

`cargo xtask clean-stale --max-size-gb N` remains the size cap for long sessions; the rules
above are what stop the cap from being hit in the first place.

**Residuals, by design:** `xtask` is excluded from hakari unification on purpose (its `ureq`
stack must not enter the product build), so `cargo build -p xtask` compiles its ~30 own
dependencies — including a `ring` — once, and the single-provider check deliberately covers
only the product graph. The former "second copy of `ahma_mcp` under `-p`" residual is gone:
`simplify` moved to its own crate behind `ahma_bin`'s feature, so every default-flavour `-p`
invocation resolves `ahma_mcp` identically to the workspace build; `ahma_mcp` now carries
exactly one cargo feature, `otel` (finding 3), off by default, so this still holds for every
invocation that leaves it off. The lean `--no-default-features` flavour is still a full second
copy of the crates it touches (5.9 GB in the baseline measurement, when it was a build; far
less as check-mode `.rmeta`); that is why it is a CI check-mode step and not a local command.
The `otel` flavour (finding 3, landed after this table was measured) is the same kind of
deliberate second copy for `ahma_common`/`ahma_mcp`/`ahma_http_bridge`/`ahma_bin`, but unlike
the lean flavour it is a real build-and-test step (not check-mode only), because release
binaries ship it — see `job-cargo-nextest`'s "otel feature" steps in `build.yml`.
